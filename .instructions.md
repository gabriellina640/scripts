# Instrucoes do Projeto

Este e um **Codex Kit Pro**: um sistema operacional replicavel para trabalhar com agentes de IA em projetos completos.

## O que e este projeto?

- Kit mestre de skills para ser copiado em outros projetos.
- Nao e um produto final; e uma base operacional.
- Organiza trabalho em produto, design, arquitetura, implementacao, seguranca, testes, performance e release.
- Mantem rigor proporcional: direto para tarefas simples, normal para features medias e rigoroso para produto/release/risco alto.

## Arquivos principais

| Arquivo | Proposito |
| --- | --- |
| `AGENTS.md` | Roteador principal de skills |
| `.codex-kit/skills/` | Skills acionaveis |
| `.codex-kit/templates/` | Modelos reutilizaveis |
| `.codex-kit/docs/` | Guias e referencias |
| `bootstrap-project.sh` | Replica o kit em outro projeto |
| `verify-kit.sh` | Valida a estrutura do kit |

## Modos de rigor

- Direto: perguntas, inspecoes, pequenos ajustes e fixes localizados. Sem design/plano formal; resposta curta; verificacao proporcional.
- Normal: feature media ou mudanca em varios arquivos. Design curto, plano curto e validacao objetiva.
- Rigoroso: produto novo, auth, dados sensiveis, banco, API publica, deploy, release ou risco alto. Usa o fluxo completo.

## Fluxo mestre rigoroso

1. Produto e escopo: `.codex-kit/skills/product-discovery/`
2. Design de comportamento: `.codex-kit/skills/brainstorming/`
3. UI diferenciada: `.codex-kit/skills/creative-direction/`
4. Arquitetura: `.codex-kit/skills/full-project-architecture/`
5. API/banco quando aplicavel: `api-design` e `database-design`
6. Plano: `.codex-kit/skills/writing-plans/`
7. Execucao: `executing-plans` ou `subagent-driven-development`
8. Qualidade: TDD, debugging, code review e verificacao final
9. Hardening: seguranca, segredos, performance, visual QA e release readiness

## Gates obrigatorios no modo rigoroso

1. Nao implementar sem design aprovado.
2. Nao iniciar sem plano executavel por tarefas atomicas.
3. Nao concluir sem validacao tecnica registrada.
4. Nao concluir sem code review.
5. Nao marcar "done" sem verificacao final.

## Quick reference

- Ideia vaga -> `product-discovery`
- Feature sem design -> `brainstorming`
- Projeto completo -> `full-project-architecture`
- UI nao-generica -> `creative-direction` + `interface-craft` + `visual-quality-review`
- API -> `api-design`
- Banco -> `database-design`
- Plano -> `writing-plans`
- Execucao -> `executing-plans` ou `subagent-driven-development`
- Logica critica -> `test-driven-development`
- Bug dificil -> `systematic-debugging`
- Seguranca antes -> `security-threat-modeling`
- Seguranca depois -> `security-review`
- Segredos/config -> `secrets-and-config-audit`
- Performance -> `performance-review`
- Release -> `observability-and-release-readiness`
- Finalizacao -> `verification-before-completion`

## Regra de codigo direto

Quando pedir implementacao direta, use:

`Only output code. Do not add comments or explanations.`

## Padrao de resposta

- Seja direto por padrao.
- Explique em detalhe apenas se o usuario pedir ou se houver risco, tradeoff, erro ou decisao tecnica relevante.
- Ao finalizar mudancas, diga somente o que mudou, onde mudou e como foi verificado.

## Seguranca minima

- Nunca commitar `.env`, chaves, tokens, certificados ou senhas.
- Validar inputs nas fronteiras publicas.
- Separar autenticacao de autorizacao.
- Nao expor dados privados em logs.
- Preferir seguranca quando houver conflito entre velocidade e risco.
